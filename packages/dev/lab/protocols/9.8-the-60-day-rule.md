# 9.8 The 60-day rule

Written 2026-10-17. Not yet run.

**Question this can falsify:** that GitHub disables `schedule` workflows in a repository with no
commits for 60 days, so the hourly sweep stops while event runs continue. This is a documentation
protocol with a one-step check: it records the rule, how the next event run notices the sweep's
absence, and the way back.

## Setup

- The common sandbox: a personal repository whose workflow checks out `hiero-hackers/sdk-automations` at the
  commit under test, builds the bundle (`pnpm install --frozen-lockfile && pnpm --filter
  @hiero-hackers/automation-runtime build:action`) and runs `uses: ./`. The run summary and the Actions
  log are the evidence. Where the real event is hard to provoke, a `workflow_dispatch` writes the
  captured payload to `GITHUB_EVENT_PATH` and runs the same step. Record the commit at step 1.
- No 60-day wait is run. The rule is read from GitHub's own documentation and the sandbox's
  Actions tab, and the evidence is the quotation and the observed sandbox state.

## Steps

1. Read GitHub's documentation on scheduled workflows and the disabling of them for inactivity.
   Record the page, the wording of the rule, and the sentence about re-enabling, quoted once and short.
2. On the sandbox, open the workflow's page in the Actions tab. Record where GitHub shows a
   disabled scheduled workflow and the button that re-enables it.
3. The one-step check: a run keeps no store, so an event run cannot know when the last sweep ran.
   Record where a missing sweep IS visible — the workflow's page in the Actions tab, or
   `gh run list --event schedule` — and that no run's summary says so.
4. Write the re-enable path: re-enable the workflow in the Actions tab, or push any commit, then
   dispatch one sweep and read `sweepFinished`.

## Expected result

The rule recorded with GitHub's own wording, and the re-enable path.
