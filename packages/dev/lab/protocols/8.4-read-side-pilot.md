# 8.4 The read-side pilot

One process, the personal sandbox, the sweep armed and writes not, on 2026-09-15:
a cold firing over every open item, then the same row made due again two minutes
later for a warm one. The measurement the read-side plan's every figure was
arithmetic in place of.

## Question

What one firing charges GitHub, cold and warm, in the client's own units and by
GitHub's own headers; and that the snapshot (D193), the batched link read (D194)
and the allowance (D192) behave live as their tests say.

## Red line

The lead's sandbox only. `APP_SLUG` unset, so nothing is written. The
configuration enabling `inactivity` in `dry-run` is put on the default branch by
the lead's own credentials for the run and restored after. The schedule row is
seeded and re-armed in the store by hand, because no delivery declares it without
a webhook; the store is a fresh file under the scratch directory.

## Method

The shell from the branch under test, `TICK_SECONDS=20`, `SWEEP_CADENCE_HOURS=1`,
`SWEEP_SHARE` at its default. The row `sweep:{owner}/{repo}` is inserted due
now; after `sweepFinished`, `due_at` is set to now again. `sweepFinished.spent`
is the client's count; the `limits` lines are GitHub's headers.

## Evidence

Two runs on 2026-09-15, both over 171 open items, writes absent. The first on the
S5 build (the snapshot in, the window slack not yet), the second on the branch's
head. GitHub's `limits` lines are the installation's own headers.

| Run | Firing | Items | Decided | Reused | `spent.core` | `spent.graphql` | Duration | GitHub `remaining` at start |
|---|---|---|---|---|---|---|---|---|
| 18:15Z, S5 build | cold | 171 | 171 | 0 | 362 | 1 | 141 s | core 4,999 · graphql 4,999 |
| 18:15Z, S5 build | warm, +2 min | 171 | 171 | 171 | 0 | 0 | 1.6 s | — |
| 18:42Z, head | cold | 171 | 171 | 0 | 366 | 1 | 141 s | core 4,995 · graphql 4,998 |
| 18:42Z, head | warm, +2 min | 171 | 171 | 171 | 0 | 0 | 1.9 s | — |

### What the runs found

- **A cold firing over 171 items charges about 365 core requests and one
  GraphQL point.** Protocol 8.3's arithmetic for the same repository, before this
  branch, was 600 to 700 requests cold and the same again warm, with a GraphQL
  query per pull request.
- **A warm firing charges nothing.** The open-item list answers 304 and every
  item is decided from its stored read; the aliased link query is not sent.
- **The first run rolled the core window twice at startup**: GitHub's reset
  header moved from 19:15:27Z to 19:15:30Z between the first responses, and a
  later reset was a new window. The head carries a 60 s slack
  (`WINDOW_SLACK_S`); the second run said `limits` once per pool and kept the
  first run's window, its `remaining` already down by the first run's charges.
- Nothing reached stderr in either run.

request use per installation" is answered for one repository; the
many-repository harness stays open.
