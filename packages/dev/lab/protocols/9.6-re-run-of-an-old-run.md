# 9.6 Re-run of an old run

Written 2026-10-17. Run nightly by `action-conformance.yml` since 2026-10-18: PASSED.

**Question this can falsify:** that a person re-running a day-old run gets facts read live, that the
stale cause is refused under `newerHumanChange` where a human acted since, and that nothing is written.

## Setup

- The common sandbox: a personal repository whose workflow checks out `hiero-hackers/sdk-automations` at the
  commit under test, builds the bundle (`pnpm install --frozen-lockfile && pnpm --filter
  @hiero-hackers/automation-runtime build:action`) and runs `uses: ./`. The run summary and the Actions
  log are the evidence. Where the real event is hard to provoke, a `workflow_dispatch` writes the
  captured payload to `GITHUB_EVENT_PATH` and runs the same step. Record the commit at step 1.
- Config `mode: active`, `triageQueue` with `welcome: true`, `arm-writes: "true"`. Do the first
  run a day or more before the re-run, and record its run id.

## Steps

1. Day 0: open a fixture issue; the run applies the label and welcome. Record the run id and times.
2. Day 0, after it: as a person, remove the label and edit the welcome comment. Record the times.
3. Day 1 or later: from the Actions tab, "Re-run all jobs" on the day-0 run. Record the new attempt.
4. Read the attempt's log. The facts must be read live (the fixture's current labels and comments),
   not taken from the original payload; the summary shows the refusal code.
5. Expect `newerHumanChange` on the label and the welcome, and zero writes: no label event, no
   comment edit after the human's.
6. On a second fixture where no human has acted since, re-run the day-old run and expect only
   `already`-style outcomes and zero writes.
7. Restore the config.

## Expected result

Zero writes from the re-run, and the refusal code in the summary where a human acted since.

## What migrated

Nothing.
