# 8.5 The prDashboard dashboard on a real pull request

The first armed run of prDashboard with every check on, against the personal sandbox,
on 2026-09-16: five deliveries on one pull request, one on a conflicting second, a
hand edit, and the first sweep firing.

## Question

That the five checks read GitHub's real shapes into one dashboard, that the dashboard
is updated in place as the pull request changes, that a redelivery duplicates nothing,
and how often `mergeable` is still `null` when the `synchronize` delivery arrives —
the measurement behind D198's open note.

## Red line

The lead's sandbox only; the pull requests the lead opened for the purpose; the
configuration enabling `prDashboard` in `active` put on the default branch by the
lead's own credentials for the run and restored after. Comment and label writes, on
the two fixtures only. The store is a fresh file under the scratch directory.

## Method

The shell from the branch under test with `APP_SLUG` set (writes armed) and no sweep
cadence, behind the smee relay 8.1 accepted; `TICK_SECONDS=20`.

| Fixture | State | Made by |
|---|---|---|
| A | one commit, no sign-off, no signature; no issue referenced | the lead |
| A′ | A with `Closes #n` added to the body, `n` assigned to someone else | the lead |
| A″ | A′ force-pushed with the commit signed off; `n` assigned to the lead | the lead |
| B | a branch conflicting with the default branch | the lead |
| `sdk-automations.yml` | `mode: active`, every check on; `applyLabels` added, then the GPG check parked, as the steps say | the lead, on the default branch |

Steps, each a `pull_request` delivery: open A; edit A′; push A″; open B; redeliver
one `synchronize` from the App's ledger; edit the dashboard by hand and push a no-op
commit. Then restart with `SWEEP_CADENCE_HOURS=1`, push to the default branch so B
stops conflicting, and read the next firing's re-evaluation of B (phase 3) and what
it charged. Reversal: close both, delete both branches, restore the configuration.

## What this run found

- Every enabled check reads GitHub's real shapes into one dashboard, updated in place
  by delivery and by sweep, one comment per pull request throughout; a redelivery on a
  store that has seen the GUID is a `deliveryDuplicate` with zero writes.
- **`mergeable` was never `null` at the moment a check read it**: six reads on two pull
  requests, including one 4 s after opening a conflicting branch and one after a
  force-push; GitHub reported `null` only in the seconds after the base moved, and the
  sweep's read minutes later found `true`. D198's open note can rest until a real
  repository says otherwise.
- The label path: a mapped label the repository lacks is created by GitHub on the add,
  grey (6.11's third question); `needsRevision` from the null position, `needsReview`
  along `revisionResolved` with the previous label removed, and `needsRevision` again on
  a fresh failure, all as the map draws them.
- An assignment made on the issue is seen on the next pull request event or sweep,
  which is what the schedule trigger is for (D200).
- Two timeline shapes the ordering reader could not read, `committed` and `reviewed`,
  each of which silenced every write on a pull request carrying one (D201). Until this
  run no armed write had been made on a pull request since #167.
- A hand edit to the dashboard does not survive the next evaluation (D145); the design
  page now says so.
- One sweep over 173 items, eight of them pull requests with every check on: 230
  requests and 161 s, before the read side's snapshot.
