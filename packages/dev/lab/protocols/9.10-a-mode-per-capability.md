# 9.10 A mode per capability

Written 2026-10-19. Not yet run.

**Question this can falsify:** that a capability's own block holds it at `dry-run` while the file
is `active` and writes are armed: on one pull request the sibling that inherits `active` writes, the
held one only rehearses, and GitHub shows the one write and nothing else (D236).

## Setup

- The common sandbox: a personal repository whose workflow checks out `hiero-hackers/sdk-automations` at the
  commit under test, builds the bundle (`pnpm install --frozen-lockfile && pnpm --filter
  @hiero-hackers/automation-runtime build:action`) and runs `uses: ./`. The run summary and the Actions
  log are the evidence. Record the commit at step 1; it must carry D236, or the file below is
  rejected as `unknownKey`.
- Config on the default branch, `heldConfig` in `src/action/configs.ts`: `mode: active`, `prDashboard`
  enabled with no `mode` of its own, `configReport` enabled with `mode: dry-run`. The workflow passes
  `arm-writes: "true"`. Restore both after the run.

`pnpm lab:action --only 9.10 --arm` runs the steps below and restores the sandbox on every exit.

## Steps

1. Record the commit. Open a pull request whose one commit edits `sdk-automations.yml`, so both
   capabilities act on the one `pull_request_target` run.
2. In the run's summary and log, expect exactly one applied effect, prDashboard's dashboard comment,
   and exactly one `wouldApply`, configReport's report. Expect configReport's `modeRecordsOnly` to
   say `dry-run, stated on its block`.
3. On GitHub, count the App-authored events on the pull request since step 1. Expect one comment,
   the dashboard, and no report comment.
4. Restore the config and the arming variable.

## Expected result

One run, one applied effect, one rehearsal, one App-authored change. A held capability's block
outranks the file's `active` and is not outranked by `arm-writes`.
