## Setup

- The common sandbox: a personal repository whose workflow checks out `hiero-hackers/sdk-automations` at the
  commit under test, builds the bundle (`pnpm install --frozen-lockfile && pnpm --filter
  @hiero-hackers/automation-runtime build:action`) and runs `uses: ./`. The run summary and the Actions
  log are the evidence. Where the real event is hard to provoke, a `workflow_dispatch` writes the
  captured payload to `GITHUB_EVENT_PATH` and runs the same step. Record the commit at step 1.
- Config on the default branch: `mode: active`, `triageQueue` enabled with `welcome: true`,
  `awaitingTriage` mapped. The workflow passes `arm-writes: "true"`. Restore both after the run.

## Steps

1. Record the commit. Open a fresh issue. Expect one run; the summary lists two approved effects;
   GitHub shows the `awaitingTriage` label and one comment by `github-actions[bot]` whose marker
   parses with the right capability and kind. Record both timestamps.
2. Re-run that same run from the Actions tab ("Re-run all jobs"). Expect decisions that find the
   work already done (`already` or an unchanged ledger read), and no new label event or comment.
3. Set `arm-writes: "false"` and open a second issue. Expect decisions, zero writes.
4. Restore `arm-writes: "true"`. Disable the workflow in the Actions tab, then open a third issue.
   Expect no run at all, so no write. Enable it again.
5. As the maintainer, delete the App's comment on the first issue and remove its label. Expect the
   resulting `unlabeled` run to ask nothing (triageQueue hears `opened` alone) and nothing re-added
   after two hourly sweeps.
6. Count App-authored actions on GitHub against the effects the summaries report applied; they
   must match exactly. Restore the config.

## Expected result

The writes land once; a re-run of the same run writes nothing; a disabled workflow runs nothing; a
maintainer's deletion of the App's comment is not fought.
