# 6.15 Lock and unlock one issue

## Question

Can the App lock and unlock one issue with `issues:write`, does the issue read expose the new
`locked` value immediately, and are repeated calls safe?

This closes the two missing endpoint rows needed by intake phase 2. It does not approve the intake
policy or enable the operations in production.

## Red line

A new issue in a personal sandbox repository only. The issue is created for this run, starts
unlocked, and is unlocked again before cleanup. No contributor issue or Hiero repository is used.
The App owner, repository, installation permissions, and approval are recorded before the run.

## Method

Use one installation token with `issues:write`. Capture the response status, rate-limit headers,
issue read, and webhook delivery for each step.

1. Create the fixture issue and read `GET /repos/{owner}/{repo}/issues/{number}`. Require
   `locked: false`.
2. Send `PUT /repos/{owner}/{repo}/issues/{number}/lock` with an empty body and
   `Content-Length: 0`.
3. Read the issue immediately and again two seconds later. Require `locked: true` both times.
4. Send the same `PUT` again and record whether GitHub still answers `204`.
5. Send `DELETE /repos/{owner}/{repo}/issues/{number}/lock`.
6. Read the issue immediately and again two seconds later. Require `locked: false` both times.
7. Send the same `DELETE` again and record whether GitHub still answers `204`.
8. Confirm the captured `issues.locked` and `issues.unlocked` deliveries name the fixture issue.
9. Close the fixture issue after it is confirmed unlocked.

Stop and restore the unlocked state if any response differs from the expected shape. Do not retry
an unclear response until the issue read establishes the current lock state.

## Expected result

GitHub documents both endpoints as returning `204` with either `issues:write` or
`pull_requests:write`. This run must establish the repeated-call behavior. Issue intake adopts only
`issues:write`:

- `PUT /repos/{owner}/{repo}/issues/{number}/lock`
- `DELETE /repos/{owner}/{repo}/issues/{number}/lock`
- read-back from `GET /repos/{owner}/{repo}/issues/{number}` field `locked`

## Migration after evidence

If the run matches the expected result:

1. Add both rows and the evidence citation to `design/findings/endpoint-permission-matrix.md`.
2. Add the endpoint shapes and transport verbs to the runtime adapter.
3. Add `locked` to the apply-time item read and prove both postconditions.
4. Replace the two unsupported shell handlers with one-call idempotent handlers.
5. Keep the capability and configuration changes in a later PR.

## Result — 2026-09-19

Approved by Farzan and run with App `4764300`, installation `163011723`, against disposable issue
`exploreriii/automation-sandbox#192`.

- The initial read returned `locked: false`.
- Lock returned 204. Reads immediately and two seconds later returned `locked: true`.
- Repeating lock returned 204.
- Unlock returned 204. Reads immediately and two seconds later returned `locked: false`.
- Repeating unlock returned 204.
- Each endpoint consumed one primary-quota request.
- Cleanup left the fixture unlocked and closed.

The App webhook was inactive, so no delivery was expected or observed. That leaves event-delivery
capture outside this endpoint proof; the adapter does not consume lock or unlock events. The
permission, response, repeated-call, read-back, and cleanup claims are confirmed by
`2026-09-19T15-34-40-128Z`.
