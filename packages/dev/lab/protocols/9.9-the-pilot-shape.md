# 9.9 The pilot shape

Written 2026-10-17. Not yet run.

**Question this can falsify:** that the five shipped capabilities run together under one file, in
`active`, from one Action workflow, each writing once through the runner's token, with no write
made twice and no two capabilities touching the same label on the same item; and that the three
capabilities no protocol has yet seen write (prDashboard, configReport, assignment) do so.

## Setup

- The common sandbox, as 9.1 describes it, at the commit under test. Record the commit at step 1.
- Config on the default branch: the full file in the harness (`harness/action/sandbox-full.yml`):
  every capability on, `mode: active`, `lockUntilTriaged` and `confirmUnlock` on, `applyLabels`
  on, `capIgnores: [blocked]`, both inactivity ladders with one-hour reminders and two-hour
  releases, every mapped label one that exists in the sandbox. `ARM_WRITES=true`.
- Runs 9.3 and 9.6 must have cleared their clocks first; this file replaces theirs.
- Fixtures: none standing; every item is opened during the run.

## Steps

1. **Triage, locked.** Open an issue. Expect in one run: the triage label, the welcome, the lock.
   Swap `status: triage` for `status: ready for dev` (adding `ready` beside the triage label is a
   two-position conflict the platform refuses, D35; removing the triage label retries the release).
   Expect the unlock and the confirmation, and nothing from any other capability.
2. **Claim and release.** On a second issue carrying `status: ready for dev`, comment `/assign`.
   Expect the assignment and its notice. Comment `/unassign`. Expect the release and its notice.
   On a third issue, still `awaitingTriage` and locked, comment `/assign`: expect no assignment
   and one notice saying the issue cannot be claimed while it awaits triage.
3. **The dashboard.** Open a pull request from a sandbox branch with an unsigned commit and no
   linked issue. Expect one dashboard comment naming the failures and `status: needs revision`
   applied. Push a signed-off commit that closes the first issue: expect the comment rewritten
   and the label swapped to `status: needs review` once the pull request is ready for review.
4. **The report.** Open a second pull request that edits `sdk-automations.yml`. Expect one report
   comment from configReport, and the dashboard comment beside it. Two writers, two comments,
   no shared label.
5. **The ladders.** Mark the dashboard's pull request a draft and leave the claimed issue idle.
   On the next sweeps expect: a reminder on each after one hour; after two hours the release of
   the issue's assignment and the close of the draft pull request, each after its own warning;
   `/working` on the issue before the second hour cancels its release and not the close.
6. **Count.** For every item, list the bot's writes from the timeline and the summaries' effect
   tables. Every write appears once; no label was set by two capabilities; every destructive act
   has its warning before it.
7. **Restore.** `mode: dry-run`, `ARM_WRITES=false`, the items closed.

## Expected result

Each capability wrote through the runner's token at least once; the counts in step 6 match the
summaries; the one-writer rule held under real timing. Anything a capability wrote twice, or any
label two capabilities both touched, fails the protocol and names the collision.
