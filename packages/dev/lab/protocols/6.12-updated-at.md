# 6.12 What moves `updated_at`

The read-side plan keys a per-item snapshot on the `updated_at` the open-items
list reports, so an item unchanged since the last sweep costs nothing. That is
safe only if every event a sweep fact depends on moves the field. GitHub's
reference says the field is "when the item was last updated" and no more.

A snapshot is keyed on this field or it is not built. Nothing below is settled
by reasoning about the documentation.

## Question

For each event the sweep's fact groups fold — assignment, a comment, a review
request, a review, a draft toggle, a push, a label, a linked-issue edit — does
the LIST row's `updated_at` change? Secondarily: does the single-item read
agree with the list, and does the pull-request read agree with both?

| Group | Reader | Events it folds |
|---|---|---|
| `assignees` | `readAssignedAt`, `readLastWorkingAt` | assigned, a `working` comment |
| `review` | `readChangesRequested`, `readReapableSince`, `readLastCommitAt` | a review, `review_requested`, `convert_to_draft`, `ready_for_review`, a push |
| `readiness` | `readDraft` | a draft toggle |
| `links` | `linkedIssues` | a pull body edit naming an issue — observed from BOTH items |

## Red line

Writes to the personal sandbox only, every one reversible, none on a fork's
head. The App holds `contents: read`, so the fixture pull request and the push
step are the lead's, through `gh` with their own credentials (as 6.9). The App
reviews the lead's pull request; it cannot review its own. No token, header or
key is written anywhere.

## Method

`harness/src/run-6.12.ts`. The App creates one issue. The lead creates one
branch, one file on it, and one pull request (`PR_6_12`, `PR_6_12_BRANCH`).
`REVIEWER_LOGIN` is a second login that may review here.

For each step: read the list (`GET /repos/{o}/{r}/issues?state=open`, paged
until the item is found), the item (`GET /issues/{n}`), and for a pull request
`GET /pulls/{n}`; cause the event; wait four seconds; read the three again.
Calls are paced two seconds apart. `--plan` prints the steps and sends nothing.
The field has second granularity, which the pace and the wait respect.

### What these runs found

- **Every event a sweep fact folds moves the item's `updated_at`**, on the
  list row, the item and the pull alike, and the three agree once the value
  has propagated. No event was found that leaves the field alone.
- **Review events propagate late.** A submitted review, a comment review and a
  dismissal set the field to the review's own instant, and the list, item and
  pull reads still return the prior value four seconds after the write. The
  new value was present at the next step, ten to twenty seconds on, and at
  thirty seconds in the deliberate recheck. Everything else — labels,
  assignees, comments and their edits, body edits, review requests and their
  removal, a push, a draft toggle — was visible within four seconds.
- **A pull request that comes to close an issue does not move the issue.**
  `links` on an issue cannot be keyed on the issue's own row; it is derived
  from the pull requests' rows, which is what the sweep already does.
- **The App cannot toggle draft on a pull request it did not author**, even
  with `pull_requests: write`: GraphQL answers `FORBIDDEN`, "Resource not
  accessible by integration" (n=2). The sweep never toggles draft; recorded
  for the failure catalogue.


## What migrates

The list-issues row in `design/findings/endpoint-permission-matrix.md` gains a
sentence naming which events move `updated_at` and which do not, with this
run's citation. The read-side plan's §2.2 takes the answer as its gate: an
event that does not move the field is either not a sweep input, or bounds
`SNAPSHOT_MAX_AGE`.
