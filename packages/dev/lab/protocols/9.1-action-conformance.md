# 9.1 Action conformance

Written 2026-10-17. Run 2026-10-17 on `exploreriii/automation-sandbox`: PASSED.

**Question this can falsify:** that each of the six captured events (the fixtures under
`packages/dev/testkit/fixtures/`), provoked for real on the sandbox, reaches a run that decides what
`packages/dev/testkit/src/journeys.ts` says it decides under the action composition.

## Setup

- The common sandbox: a personal repository whose workflow checks out `hiero-hackers/sdk-automations` at the
  commit under test, builds the bundle (`pnpm install --frozen-lockfile && pnpm --filter
  @hiero-hackers/automation-runtime build:action`) and runs `uses: ./`. The run summary and the Actions
  log are the evidence. Where the real event is hard to provoke, a `workflow_dispatch` writes the
  captured payload to `GITHUB_EVENT_PATH` and runs the same step. Record the commit at step 1.
- One configuration per capability, each enabling that capability alone, in `mode: dry-run`, with
  `arm-writes: "false"`; the config text is `configFor` in `journeys.ts`. Switch the file between
  capabilities; binding is read live on each run.

## Steps

1. Record the commit under test and the bundle build's exit code.
2. For each capability (`triageQueue`, `prDashboard`, `inactivity`, `configReport`, `assignment`),
   set its config, then provoke each capture in turn: open an issue (`issues.opened`), label it
   (`issues.labeled`), comment on it (`issue_comment.created`), close it (`issues.closed`), open a pull
   request (`pull_request.opened`; for `configReport` it touches `sdk-automations.yml`), close it
   (`pull_request.closed`).
3. For each run, read the job summary and compare the decision rows (capability, verdict, code) with
   that capability's cell in `JOURNEYS`. A cell absent from `JOURNEYS` expects no rows.
4. `inactivity` hears the schedule alone: run it once from the hourly schedule (or
   `workflow_dispatch`) and expect no row from any of the six events.
5. Replay one captured payload through `workflow_dispatch` and compare its summary with the real
   event's; any difference is a finding about the capture, not about the engine.
6. Confirm GitHub shows zero writes by the run: no label, comment or lock changed.

## Expected result

Every run exits 0 and its summary shows the `JOURNEYS` row for that capability and capture: two
`triageQueue` effects on `issues.opened`, one `prDashboard` effect and one `configReport` effect on
`pull_request.opened`, nothing elsewhere. Each effect reads explained, would apply, recorded only.
